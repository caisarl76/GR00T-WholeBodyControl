# PRD — Continuous PICO manipulation and walking

- Revised: 2026-11-12. Owner: caisarl76.
- Basis: [approved continuous-height design](2026-11-12-continuous-height-manipulation-design.md).
- Status: design approved; this revision specifies the implementation and validation work. Phase B remains stopped at Task 6. No new runtime results are claimed.
- Historical baseline: [pre-revision PRD](archive/2026-11-12-pico-manipulation-before-continuous-review.md). Its superseded controls, thresholds and eligibility rules are not implementation instructions.

## 1. Problem

Full-body POSE mode can translate operator body-estimation errors into unwanted robot torso and leg references. The planned arm-only mode separates controller wrist intent from joystick posture/locomotion intent, but the session-long walking ban after any height change prevents a complete pick-and-deliver episode. Mode/recording conflicts, primitive hand takeover and a posture-changing timeout response also obstruct that task.

## 2. Goal

One policy session and one recording must support: walk to a surface; stop; use joysticks to lower and bend; reach/grasp with controller poses and hand primitives; withdraw the object; manually raise/straighten while holding it; choose a carry arm pose; turn/walk; stop, adjust and place. Also support a low-to-high transfer with stationary feet and no walking request.

Height and waist stay joystick-controlled while grasping. There is no automatic stand-up or arm tuck. Controller wrist motion changes arm references; joystick input changes requested posture or locomotion. SONIC retains balancing authority. Success means bounded unintended motion and task completion, not physically immobile waist and legs.

## 3. Scope

First validate free objects with measured mass, dimensions, grasp, friction and carry pose. Do not claim an unspecified G1 payload capacity. Raised and lowered carry-arm configurations need separate evidence. Drawer/door use remains a required later contact extension, with its own frame, state estimation and compliance/force validation.

Retain existing planner/SONIC initially. If it cannot track and balance the supported loaded motions, report the capability gap and propose a controller/sensing change; gating cannot replace balance control. Default sessions without the manipulation flag preserve their existing behavior. No commits or branch changes are authorized.

## 4. Anti-goals

- A mode change, timeout or recovery unexpectedly raises the body, releases a hand or discards the episode.
- Any height history permanently prevents completing the episode after physically recovering.
- The system accepts a stale input or silently records an unavailable command as a valid default.
- A small reference error is treated as proof of balance, grasp retention or obstacle clearance.
- Mandatory waiting interrupts normal joystick body adjustment during stationary manipulation.

## 5. Operator experience

### 5.1 Controls and persistent state

| Mode | Wrists and hands | Left stick | Right stick |
|---|---|---|---|
| MANIPULATION | Controller wrist deltas; explicit hand primitives | Y: height, X unused | Y: waist pitch, X: waist yaw |
| FROZEN / carry selection | Hold actual last-sent arm and hand references | X/Y: requested movement | X: requested heading; Y ignored |

B+Y selects MANIPULATION or FROZEN; it preserves heading, requested height/waist and hand/arm commands. Selection alone never starts locomotion. In FROZEN, an unsuitable posture causes a temporary refusal with a reason. Return to MANIPULATION to adjust it. During walking, keep carry references fixed; first stop to reposition arms, height or waist.

Stationary MANIPULATION permits simultaneous bounded wrist and height/waist motion while grasping. It requires neither walking readiness nor an intermediate standing pose. A high placement posture need not be suitable for walking.

### 5.2 Hand primitives

Persist each hand's selected primitive and actual last-sent command separately from the motion mode. OPEN requires a deliberate new input event. Mode changes, loss/recovery, controller re-anchoring or a trigger already released on re-entry never imply OPEN. The old 5% takeover rule is withdrawn: the current trigger mapping is discontinuous at 0.5 and ignores grip.

First-version mapping (implementation choice): in live MANIPULATION, trigger hysteresis selects the existing middle-close preset at >= 0.6 and OPEN at <= 0.4. Between thresholds retain the primitive. After entry/recovery, require first matching the held primitive's input side; that match only arms control and does not change the hand. Only a subsequent opposite-threshold crossing changes the primitive. Invalid samples never arm it. This prevents held CLOSE + live released trigger from reopening on re-entry. Grip has no hand-primitive role in this first mapping. Each hand is independent; changing presets later needs explicit mapping and tests.

OPEN additionally requires <=0.4 continuously for at least 100 ms over at least three distinct fresh backend samples, with no inter-sample gap above 50 ms. A single valid-marked zero/dropout cannot release. A rebound above 0.4, invalidity, backwards sample time, excessive gap or leaving live control cancels the pending release. Duplicate samples earn no duration or count; expiry still cancels while duplicates are arriving. Prefer verified acquisition timing. If acquisition timestamps are unavailable, use local monotonic elapsed time over at least three distinct backend update events whose freshness and delivery bound G3 verifies; count each update once, even if its trigger value is unchanged. Cached streamer ticks and merely different numeric values are not new samples. This arrival-timed debounce is a separately declared backend capability, with queued/batched delivery and one-sample dropout tests. Without either verified path, release remains unavailable until G3 passes; do not imply every backend has acquisition timestamps. Entry matching remains necessary. These are conservative interaction defaults to validate at the supported backend rate, not measured grasp guarantees.

Transitions between actual hand commands blend over 0.2 s from the actual last-sent value; interruption/reversal starts there again. These are initial interaction settings, not proof of retention. Validate actual pickup and carry, including boundary noise and re-entry.

### 5.3 Mode and recording controls

OFF -> PLANNER via A+B+X+Y; PLANNER -> MANIPULATION via B+Y; MANIPULATION <-> FROZEN via B+Y. Under the flag disable POSE, VR_3PT and locomotion-mode cycling; the first gait is SLOW_WALK at the validated speed range. All four buttons while running stop the policy immediately. This is distinct from the robot emergency stop.

Retain 150 ms exact-set debounce for non-stop chords, all-button release to re-arm, and release-before-start. Ignore entry chords while entry is pending. While walking, a MANIPULATION request first enters controlled stop; anchor only after stop completes.

The user requires recording without a second person. In manipulation sessions reserve both thumbstick clicks held for 0.75 s: START from confirmed IDLE, or STOP_AND_SAVE from confirmed RECORDING. This is an explicit action selected from exporter-confirmed state, never a blind toggle. Both backends expose stick clicks; menu buttons are unavailable on Isaac Teleop. G3 must verify click freshness too.

Recording is available before the first walk: startup HOLD with no gait initiated, or policy OFF, permits recording without a previous stop or walking-readiness profile. After gait, its controlled stop must finish before a new recording gesture. Recording never starts the policy or grants locomotion permission.

Enter with sticks centered within 0.15 and both clicks released for 150 ms. The first click holds body/arm/hand references and cancels pending walk intent; the second must arrive within 200 ms and both stay fresh/centered for 750 ms. Deflection, loss, an incomplete pair or face-button chord cancels recognition without replaying suppressed motion. Motion chords retain priority, especially immediate policy stop. A click while walking requests controlled stop only; a new gesture is needed after stopping. Re-anchor to held wrists and require release/neutral re-arm before further deliberate motion. There is no controller discard gesture.

Keep recording control small: one-shot explicit START or STOP_AND_SAVE, plus exporter-published IDLE/RECORDING/SAVING/SAVE_ERROR state and episode ID. Choose the action from state received within 500 ms; stale/unknown state produces “recording status unavailable” and no action. START in RECORDING is a no-op; STOP_AND_SAVE in IDLE or SAVING is a no-op. STOP_AND_SAVE in SAVE_ERROR retries saving the retained episode. The next gesture or keyboard c retries; there is no separate retry action. State-based idempotence covers repeated actions while the episode is current, not arbitrary replay across later episodes. Do not queue commands for reconnect or automatically retry a timed-out action. Mark any ambiguous/late boundary for review rather than claim exactly-once transactions.

Hold motion for at most 1.0 s after dispatch, ending earlier on applied-state confirmation (RECORDING for START; SAVING/SAVED or SAVE_ERROR for stop/save). At the deadline clear the recording-induced hold, announce “recording boundary unconfirmed,” and allow normal motion after release/neutral re-arm. Saving may continue in the background. Lost feedback, exporter crash or save failure never creates a persistent motion latch; independent robot/controller interlocks still apply. A late state update can reconcile the recording status but cannot restore the expired hold. The operator can repeat the gesture after fresh state arrives. Immediate policy stop always remains available.

The exporter announces applied state: “recording started,” “saving,” “saved,” or “save failed”; do not announce success on button press. Verify an audio route the headset wearer can hear. Task 14 launches a real terminal publisher for the exporter's localhost:5580 subscriber. In manipulation sessions keyboard c directly starts, stops/saves or retries based on exporter state; x directly discards. Neither requires a manager connection or motion-hold handshake, so save/discard still works after manager failure. Record the actual boundary and its source; a keyboard action during movement is a deliberate recording action, not a robot control. Unflagged c retains the legacy three-step cycle. Suppress A/B+grip recording shortcuts at their initial edge; default-session shortcuts remain.

### 5.4 Joystick references

Retain deadzone 0.15 and rate control: release holds requested values. Initial rates are height 0.1 command units/s, waist yaw 0.5 rad/s and pitch 0.3 rad/s. Retain command limits height [0.2, 0.8], yaw +/-0.6 rad, pitch [-0.1, 0.4] rad, roll 0 as candidate software limits; physical operating limits must be narrowed by validation.

Untouched height is -1. First use starts from G1's calibrated H_default, not a range edge. Send changed height at most 5 Hz with 0.01 command-unit quantization, and the exact final value at the next allowed slot. Command height is not calibrated metres of pelvis motion; use G1's map. Saturation must not accumulate hidden error.

## 6. Technical design

### 6.1 Command path and state ownership

At >=20 Hz the manipulation streamer sends planner mode/movement/facing/height, 17 upper-body references (waist 3 plus arm 14, existing interleaved order), and both hand commands. Do not send VR 3-point or SMPL targets. The deploy substitutes upper-body references into policy observations; this does not provide a separate whole-body balance solve.

Keep requested intent, last transmitted command, deploy-applied command and measured state distinct. The streamer owns input mapping, anchors and transition intent. The deploy owns applied references, fault handling and authoritative locomotion acceptance. An acknowledgment proves processing, not physical recovery. New manipulation-only fields and feedback carry session/command identity so delayed feedback cannot authorize a different transition.

### 6.2 Wrist mapping and IK

Retain the earlier PRD's coordinate conversion and anchor-delta formulas: convert controllers to robot axes, capture headset yaw as the operator frame, and apply position/orientation deltas to commanded wrist anchors in torso_link. Scale starts at 1.0. First entry uses fresh measured joints; later re-anchors use the last applied/held command, never zeros.

Precisely, W is the controller world converted to robot axes (x forward, y left, z up); O is fixed by headset yaw psi0 at anchoring; T is torso_link. With controller anchor (p_c0, R_c0) and commanded torso-relative wrist anchor (p_w0, R_w0): delta_p = Rz(psi0).T @ (p_c-p_c0); delta_R = Rz(psi0).T @ (R_c @ R_c0.T) @ Rz(psi0); target_p_T = p_w0 + delta_p; target_R_T = delta_R @ R_w0. Re-anchor on re-entry using the current headset yaw and held command, preserving heading. Follow the existing Unity-to-robot conversion before these formulas.

With a stationary controller, raising the torso lifts the hands; waist motion also rotates them. Wrist input adds torso-relative movement. World-fixed pose or constant object orientation is not promised. Operator withdrawal clears the surface before body lifting; initial trials use a known clear fixture with represented object geometry. No automatic clearance sensor is assumed.

Arm-only IK moves 14 joints. Preserve joint limits and bounded applied steps; report QP status, FK residual, measured wrist error and clearance separately. Re-seeding can recover a stall but failure of one seed does not prove unreachability or a closest solution. Large unresolved error is visible and prevents accepting a new carry configuration. Verify the full guarded solve/reseed tick still meets the 10 ms p99 budget on the teleop PC; G2 covers only its existing prototype.

### 6.3 Manual posture adjustment and recoverable walking

In static control, -1 uses IDLE and explicit height uses IDLE_SQUAT because G1 found IDLE ignores explicit height. Height and waist remain manual during grasping. Do not apply a walking-readiness dwell to normal manipulation input.

Walking readiness uses the narrow flat, non-slip-floor assumption in Task 3c: feet are assumed planted after a completed controlled stop, with a declared free object and carry configuration. No slip/contact sensor is required or claimed. The separately validated predicate checks joint/FK posture conditional on that assumption, waist/tilt, arm extension and declared object/load setup; complete relevant reference transitions; bounded residual motion/tracking over a causal dwell; fresh complete feedback; valid controllers; stop/re-arm and watchdog conditions; completed optional lock release. The load setup is a declared validated configuration, not automatically measured payload.

A posture change, unexpected disturbance, stale feedback, loss or watchdog event invalidates readiness. The operator can correct the condition and request walking again within the session. No session-long height-history latch is part of the intended product. A held refused stick cannot start later: neutral then a new deflection is required. Turning is locomotion and has the same authorization, including turns sent in a nominal static planner mode.

First locomotion is standing-height only. Keep the handoff on a fresh walk request after initial readiness, not on carry selection; hand off to IDLE/-1, then re-evaluate the physical configuration and dynamics with fresh applied-command evidence before starting gait. Reassess after any optional waist-lock release too. The earlier 0.5 s handoff and 4.5 s rest are experiment-specific starting candidates, not unconditional permission. On stop retain standing posture; never silently restore an old lowered value. Requested and sent heights remain separately logged. A reference-changing handoff requires a new 1 s window plus 0.5 s dwell; unchanged sentinel/stop state with current readiness does not restart this history merely because a new request arrives. The experiment calibrates separate explicit-height and post-sentinel/post-stop stance references.

The readiness evaluator also operates on deploy-local fresh state, so delayed streamer commands cannot bypass it. During gait use a separately validated stop/fault predicate; ordinary gait motion must not be tested for standing still. Restarting clears neither physical recovery requirements nor load assumptions.

Each controller sample has a freshness timestamp/sequence distinct from planner-message transmission. Repeating an old controller sample in a new command cannot qualify neutral re-arm, hand release or a fresh walk request. A deploy-generated applied epoch changes on every relevant applied-reference, sentinel handoff or optional lock change; readiness certifies that epoch, not only the streamer's command number.

Use the deploy-clock echo protocol in the [Task 3c contract](2026-11-12-manual-recovery-protocol.md): commands echo a recent deploy-issued snapshot ID and t_mono_ns, bound to that deploy process. Deploy checks age in its own clock, without comparing monotonic clocks on separate hosts. The co-hosted reader/streamer recomputes each sample age at command serialization, including cached residence and any G3-verified backend delay bound; it must be <=50 ms. Together with a transmit echo <=100 ms old at deploy, this gives a conservative <=150 ms sample-age bound at acceptance. No per-sample challenge binding is needed. Backend freshness remains a separate G3 requirement; a new echo cannot reset sample age. Publication time is not sensor acquisition time; export sensor receipt/sequence and validity separately.

New identities, sequences and times use exact nonnegative signed 64-bit integers with checked ranges. The planner extension uses a versioned compact i64 block within the existing 1,280-byte header. Feedback packs integer fields directly, bypassing the double-valued visualization map. Default planner messages remain byte-identical. Test integers above 2^53, malformed types/shapes, overflow and worst-case header size. Task 11a implements identity/applied state/HOLD independently; Task 11b's readiness/profile evaluator starts only after Task 3c establishes a feasible candidate under explicit sensing assumptions.

Neither failed stillness detector is adopted. Missing sensing, limits, a mismatched validation profile or a failed recovery experiment disables recovery-authorized walking in prototypes. That is a development limitation, not a completed product. The new protocol must test actual loaded transitions as well as detector labels and declare sensing limitations and causal detection delay in advance. Simulator ground truth is for scoring only.

### 6.4 Waist lock

First loaded validation uses lock off. Retain optional two-key experimental locking only for IDLE/IDLE_SQUAT, with 100 ms message freshness, 0.5 s blend-in and 0.2 s blend-out. Lock release uses monotonic request/ack sequence and alpha from one fresh sample, including acknowledgment when the deploy flag is disabled. A stale/reordered sample cannot complete the request. Release timeout remains 0.5 s; timeout requires a new operator request.

Lock release does not prove readiness. Re-evaluate after the change. Lock-on loaded behavior is a separate validated configuration, never inferred from lock-off results. Balance authority and measured residuals matter more than making waist error numerically zero.

### 6.5 Entry and transitions

Entry requires valid fresh feedback (<100 ms), both valid controller poses and acceptable anchor IK; otherwise preserve the previous state. Do not anchor to zeros. Waist initializes once from measurement and subsequently changes by stick only. Re-entry preserves commanded arm/hand state and heading. A walking-to-manipulation request completes a controlled stop before anchoring.

Transition sequence: MANIPULATION -> carry selection -> pending authorization -> sentinel/lock handoff -> fresh readiness -> WALKING -> controlled STOP -> carry or MANIPULATION. No transition automatically raises, straightens or tucks. A refusal allows returning to manipulation. State and reason are visible and recorded.

### 6.6 Faults and controller validity

Use backend per-controller validity/sample freshness. Identical pose is not loss. Retain 6 m/s sample-speed outlier guard, three good samples to reacquire and 0.5 s continuously valid recovery. A backend with no verified per-controller freshness gets no stick-driven height, waist, walking, turning, hand release or controller recording events; label it unsupported for the complete workflow. Grasp remains held, with explicit recovery/emergency procedures; do not reinterpret stale trigger data as deliberate release.

On a controller loss hold that arm and hand, center its sticks and invalidate walking readiness. Either controller loss during gait stops it in the first configuration. Recovery re-anchors to the held applied reference and requires primitive matching/re-arm. Source timestamps and arrival times both matter; receipt of a delayed sample does not make it current.

For a 200 ms planner-input timeout during a stationary low grasp, preserve the height-effective static mode, height, heading and applied upper-body/grasp references; do not substitute IDLE for IDLE_SQUAT. During gait initiate the tested controlled stop. Keep a latch until >=150 ms of fresh valid physically neutral inputs, then require fresh walking intent and readiness. Holding references does not guarantee physical immobility under load.

Without --manipulation, retain the existing 1,000 ms timeout and its IDLE/-1 fallback with upper-body and hand overrides dropped. Regression-test this default explicitly. B+Y through the real manager/deploy must not reset heading, applied references or grasp when the manager repeats a start message; unit-level state preservation alone is insufficient evidence.

The returning arm/waist reference stays limited to <=1 rad/s per joint until all joints are within 0.01 rad of their moving target. Preserve hand primitive independently. On stale feedback in the streamer freeze new posture/arm reference changes and invalidate readiness; deploy retains its local fault authority. A QP failure holds the applied solution, and continuous failure over 0.5 s enters that arm's recovery path. Large unresolved FK error is not silently reported as safe reachable motion.

### 6.7 Recording

One episode spans all modes. Record requested/sent/applied references, hand primitive and command, mode/transition, controller validity/source time, feedback age, readiness/refusal, fault state and config IDs. Correct the current mode-5-only planner filter for manipulation-session planner modes. Represent missing/stale data with explicit validity; retain numeric placeholders only with false validity. Preserve default schemas unless explicitly opting into manipulation recording.

An exporter without --manipulation that receives mode 6 must report a schema mismatch and refuse/fail the recording, never save zeroed planner labels as valid data. The launcher propagates the flag to manager, deploy and exporter and starts the keyboard publisher. Controller actions and exporter-published applied state are recorded; Task 16 must start and save through the actual transport and verify the resulting artifact, including loss, duplicate and late-subscriber cases.

Audio verification is a separate human checklist, not an automated claim: record operator name/sign-off, date/time, headset/backend, audio route, code/config identity and whether each start/saving/saved/error/unconfirmed cue was heard. Task 16 validates the attached signed artifact; missing, failed or mismatched evidence fails the audio acceptance item. Automation never supplies the sign-off.

## 7. Acceptance

Existing isolated reference/mapping/chord tests remain useful; historical test numbering is in the archived PRD. Replace obsolete tests for permanent walking disable, input-distance hand takeover and abort-on-B+Y with the current contracts.

### 7.1 Physical measurements

Use independent MuJoCo pelvis/body/object truth to score sim; the deploy's constant base-position placeholder is not a measurement. Use actual wrist FK and object motion, not reference continuity alone. Distinguish controller/model error from measured robot error. Define posture/load range, balance limits, retention, clearance, placement accuracy, settling/dwell, false accepts/refusals and time-to-ready before collecting validation data. No universal loaded thresholds are adopted by this revision.

### 7.2 Required scenarios

| Scenario | Required outcome |
|---|---|
| Full walk/pick/carry/place | Complete one recorded episode with manual body adjustment and a real grasp; walking becomes possible again after correction; no session reset |
| Low-to-high transfer, feet stationary | Simultaneous joystick body and wrist control remains responsive with grasp retained; no mandatory standing pose or readiness wait |
| Hold CLOSE, leave at trigger 0.51, return at 0.49 or released | No opening or mode-induced release; matching and a new opposite-threshold event are required |
| Mode chords with grips held | No recording toggle/abort; dedicated two-click recording and keyboard fallback remain effective |
| Armed CLOSE with one fresh valid-marked trigger zero | Grasp held; only a sustained fresh deliberate release opens |
| Solo recording, nominal case | Applied START/STOP_AND_SAVE, audible confirmation, saved artifact, no unintended gesture motion |
| Recording loss/crash/error | Recording hold clears within 1 s; boundary unconfirmed is reported; normal deliberate motion can resume; direct keyboard save/discard works without manager |
| Bent waist / extended arm / low height then walk or turn | Refuse unsuitable carry configuration; manual correction and new request can succeed |
| Reference/lock/sentinel change while pending | Previous readiness becomes invalid; fresh applied-state evidence required before gait |
| Controller loss, delayed/stale feedback and network loss during low grasp | Preserve appropriate static reference and grasp; no unintended IDLE rise |
| Loss during gait and held input on reconnect | Tested controlled stop; neutral/re-arm and new readiness before motion resumes |
| Reach/reseed/arm-down with object | Bounded reference steps and tested clearance; error remains visible; no claim of closest feasible solution from QP status |
| Recorder through all states | One ID, accurate planner labels, explicit validity and complete transition evidence |

Run each approved free-object trajectory/configuration five times; release requires every run within pre-registered task limits. Vary heights, arm/carry poses and loads within the declared range. Calibrate on separate data and freeze source/configs before held-out validation. Drawer/door results do not carry over from free objects.

## 8. Risks and limits

The existing planner/SONIC may not balance arbitrary manual upper-body references or loads. Current feedback may not observe support/slip or pelvis translation sufficiently. Torso-relative targets move through the world during body changes. No gate can guarantee arbitrary contact clearance or payload stability. These are measured capability limits that must constrain the supported workflow or trigger a controller/sensing redesign, not increasingly restrictive timers that make the task impossible.
