## 1. Question and current feasibility result

Can the operator manually lower/bend, grasp, withdraw, raise/straighten and then walk again while retaining the object, using an observable, useful transition decision? A second required task moves an object from low to high with stationary feet and no walking request. Body and wrist input stays live during that task; a readiness dwell must never block those intended movements.

Selected scope: flat, non-slip floor; a declared free object; feet assumed planted after a completed controlled stop. C1 tests whether the robot has returned to a suitable joint/tilt posture with bounded residual motion. It does not certify global position, contact or slip. This is the narrower option proposed in the user review; adding support sensing is not a prerequisite for this candidate.

The choice fits the problem: G1 measured unsuitable height-command/gait behavior, while Step 9 disproved one stillness formula. Neither establishes a requirement for a general slip detector before any recovery walking can be attempted. Existing default walking without slip sensing is context, not proof that loaded recovery works. That proof still requires the new loaded handoff and episode trials.

Hardware slip remains a declared residual risk. FK assumes planted feet and cannot verify that assumption. Sim truth audits foot displacement/support and physical outcomes offline, never as a live input. Trials deliberately outside the floor/support scope are labeled before recording; a spontaneous slip/fall during a nominal in-scope trial is a failure, not a convenient post-hoc exclusion. Task 11b is now reachable after this protocol's review and Task 6, without a separate sensing redesign. A failed C1 remains a failure; no withdrawn check is re-enabled.

## 3. Cross-host freshness owned by Task 11a

Use challenge/echo in the deploy's clock. No NTP/PTP or teleop-to-robot monotonic offset estimate is required by this design. This is protection against stale/reordered data under cooperating processes, not network authentication.

1. Each deploy start generates a positive random 63-bit deploy_instance. Feedback carries increasing feedback_seq and t_mono_ns. Check an echoed seq/time pair against recent issued feedback from this instance, with 0 <= now_deploy - echo_time <= 100 ms and increasing command sequence. This bounds feedback-command transit without synchronizing host clocks.
2. Reader and streamer share a host/monotonic clock. Immediately before serializing each command, compute sample_age = now_serialize - acquisition_time_in_reader_clock. If acquisition time is unavailable, use now_serialize - verified_update_arrival + G3's measured conservative backend delivery bound. Both formulas include cached residence. Require age <=50 ms; a cached age value computed earlier is invalid. Backend delay must be bounded separately; merely stamping a polled cached value as received-now is insufficient.
3. The echo was issued before serialization, so command transit is at most the echo age at deploy. Thus sample age on acceptance is conservatively <=50+100=150 ms. Deploy can check reported sample_age + echo_age <=150 ms as well as both individual limits. Recheck age at the control tick that applies the command, including any local queue time. No per-sample challenge, ordering proof against a robot challenge or cross-host clock mapping is needed.
4. Preserve sample sequence/source time and validity across repeated sends, while recomputing age. Same-sequence payload/source changes are malformed; reported age must grow. Distinct verified updates, not fresh planner packet IDs, earn neutral/trigger/click duration. A fresh command echo cannot make cached input fresh. With acquisition timestamps, debounce uses acquisition intervals; otherwise use local monotonic time at distinct verified update arrivals, reject batched/queued replay and gaps >50 ms, and validate that fallback in G3. Identical trigger values on independent updates remain valid.
5. Session/deploy restart clears pending movement, partial gestures and readiness. New sessions enter HOLD with fresh neutral re-arm; old session packets cannot switch it back. Reject malformed/stale commands without renewing watchdog freshness. Final walking acceptance also uses fresh local robot sensors/current applied epoch. READY feedback is display information, not a transferable authorization token.

Task 11a tests asynchronous backends, arbitrary host-clock offsets, stalls between acquisition and serialization, asymmetric network delay, delayed deploy application, duplicate samples and cached values with fresh packet IDs. The 50/100/150 ms figures are explicit transport budgets, not physical settling thresholds. G3 must demonstrate the chosen sample-age provenance; inability to do so is reported honestly rather than disguised by locally incrementing counters.

### Exact wire representation

Optional planner field manipulation_meta is little-endian i64[18]. Order:

| Index | Meaning |
|---|---|
| 0 | Schema version (1) |
| 1–4 | deploy_instance, manipulation_session, command_seq, reference_epoch |
| 5–7 | motion_intent enum, op_neutral 0/1, two-controller validity bitmask |
| 8–9 | transmit echo feedback_seq, echo t_mono_ns |
| 10–13 | Left sample seq, source time ns (0 if unavailable), age at serialization ns, fresh 0/1 |
| 14–17 | Corresponding right sample values |

Times/counters are nonnegative signed i64, process IDs positive 63-bit. Zero/false cannot stand for available data unless explicitly valid. Unknown enums, wrong block version/shape/dtype, negative values, overflow and noncanonical masks are rejected. Do not route uint64 through the Python packer's float32 fallback. Missing extension in a default session preserves existing message bytes; missing extension in a manipulation session refuses it. Check full optional planner metadata against the real 1,280-byte header capacity; do not change framing to fit individually named scalars.

Feedback identities/epochs are direct msgpack integers with checked i64 range, never entries in the double-vector visualization map. The existing t_mono_ns value can remain an integer on the legacy path; manipulation encoding range-checks it before using i64. Test 2^53+1 and boundary values through Python -> actual C++ decoder -> actual feedback -> Python. Task 11a excludes ready_epoch/profile metadata; Task 11b adds them only for a feasible candidate.

## 4. C1 under the planted-feet assumption

Inputs: measured absolute q/dq, calibrated base IMU quaternion/gyro, applied references and epochs, current static/planner state, fresh controllers and the declared carry configuration. Use the available torso IMU as a separately timed diagnostic; it is not an extra undocumented prerequisite. No support sensor, integrated acceleration, torque/contact estimate, world velocity or sim truth enters C1.

Posture envelope: compare leg q to the context-appropriate frozen reference bank for the declared carry configuration; bound base tilt, measured waist angles, arm tracking error and membership in a frozen approved arm configuration (measured arm q within 0.10 rad of its stored q14). This prevents accurate tracking of an arbitrary extended-arm reference from masquerading as a validated carry pose. FK foot-to-pelvis height is an optional diagnostic conditional on planted feet; C1 does not require absolute pelvis-height sensing. This catches a crouched/bent configuration without claiming to distinguish every quietly displaced pose.

Dynamics: on a trailing 1 s window, calculate peak absolute leg dq, peak gyro norm, max-minus-min leg q per joint and total absolute leg-q path length. Require all features within the selected §6 limits for a further 0.5 s, with no relevant applied-reference change in that history. No endpoint subtraction or signed gyro averaging. A quiet hand/arm carry reference must also satisfy its tracking limits. The previous failed peak and endpoint detectors supply counterexamples; none of their adopted thresholds or runtime code are reused.

C1 is a feasible candidate to implement from existing signals **under the chosen assumption**, not a demonstrated useful classifier. Noise may make peak/path-length conditions too restrictive. If all predeclared candidates reject usable holds or allow bad loaded transitions, report FAILED and redesign; do not enlarge the grid after seeing holdout data.

| Case | Treatment |
|---|---|
| Low/bent posture or extended arms outside chosen carry pose | Reject by joint/tilt/tracking envelope; test real walk requests |
| Out-and-back sway | Test non-cancelling window features and actual accepted gait outcome |
| Quiet displacement under an external held force | Declared contact stress outside free-object scope; retain and report response, no general detection claim |
| Common foot slip or global translation | Unobservable residual risk. Offline truth audits scope; never feeds acceptance |
| Wrong object/load or drawer/door contact | Outside this profile; no automatic payload/contact recognition promised |

Deliberately slippery-floor/support-removal/held-external-force cases are separate diagnostic blocks registered in advance. An unexpected violation in a nominal flat-floor case fails that configuration. No pass may be assembled by dropping nominal failed cases as “out of scope.”

## 5. Transition and stopping contracts

Readiness is considered only for locomotion, including pure turning. During stationary manipulation, normal bounded joystick and wrist commands remain available irrespective of readiness. Carry selection holds the operator-selected references and grasp. A refused request is consumed; the operator corrects the condition, neutralizes the stick and makes a new request.

Product choice for this revision: retain handoff on a fresh walk request, not merely on carry-mode selection. With a validated candidate, check the current supported carry envelope and dynamics; then authorize only the static sentinel handoff/optional lock release. That change increments applied_epoch and discards earlier history. Re-evaluate using fresh samples from the new epoch before gait starts. The operator has already manually raised/straightened; the handoff must not create an automatic lift/tuck or large change. Any excessive handoff response is a physical failure, not something to wait through until the classifier eventually passes. A reference-changing handoff therefore adds at least 1.5 s (new 1 s window plus 0.5 s dwell); report this separately from time to initial readiness. If already at unchanged IDLE/-1 with completed stop and current readiness, do not resend a synthetic transition or discard valid history just because the stick moved. Carry selection by itself never changes the static mode/height. Moving handoff earlier remains a later latency choice, with its own continuity check.

Applied-reference changes, stale input/sensors, profile/configuration change, watchdog recovery and observed disturbances invalidate standing readiness. The first detectable response to an unobserved external force is necessarily delayed; enumerate this latency rather than claim zero delay. No standing predicate is evaluated during normal gait as if moving legs meant failure. Walking uses profile-specific gait guards and controlled stop.

A controlled stop has separate evidence: movement/turn intent zeroed; planner gait transition completed; the declared planted-feet assumption and measured joint/tilt/dynamics within its stopping envelope for its own dwell; no stale queued gait command. Neither “IDLE has been sent” nor a fixed timer proves stop completion. Specify stop command, delay and maximum travel/turn limits before trials, including faults while holding an object. Only after stop completion may stationary recording/anchor transitions proceed.

Task 11b's future profile must identify platform, controller/model hash, joint/frame calibration, support_assumption=flat_floor_planted_after_stop, object/carry/terrain configuration, feature definitions/window, limits and error margins, dwell, sensor max age/skew, detection/stop latency and independent validation artifact. ready_epoch is present only while that exact profile accepts the current applied_epoch. Changed profiles invalidate prior history. Hardware and sim profile namespaces are separate.

### 6.2 Setup-grasp accounting for every new case

A setup attempt begins when the scripted approach starts and lasts at most 20 s through first unsupported lift. Permit at most two retries (three attempts total) from the exact same initial robot/object pose, seed and fixed approach, resetting the scene only between attempts. Log all attempted pickups and failure reasons; no seed/pose/grip adjustment between retries. Failure to establish pickup within the budget fails that mass/carry configuration and stops its campaign; it is never erased as an invalid setup. An actual software/model failure aborts the campaign for repair and amendment rather than cycling through retries.

The setup retry applies only to a miss while the object remains on its intended pickup support, before its first unsupported lift. Slip/drop after first lift, including transport into the carry pose before the nominal timed marker, is a case failure with no setup retry. Calibration, matched disturbance controls and the grasp preflight obey the same rule. Full E episodes include pickup as task behavior: a pickup miss/drop fails that repetition rather than being reset inside an otherwise “successful” episode. Publish denominators for setup attempts/retries, acquired cases and all failures. No successful later attempt removes a preceding failure from the report.

### 6.4 Trial matrix and frozen order

Development uses seeds 1101/1102; validation uses 2101/2102/2103 and new initial object xy offsets (-10,0), (0,10), (10,-10) mm respectively. Run cases ordered by mass, carry pose (raised then lowered), direction (forward/backward/turn), then request delay. No random order selection after outcomes. Pin exact seeded trajectory files in the manifest before either split; closed-loop joystick/controller trajectories use the real integrated path.

- Nominal R: 2 masses x 2 carry poses x 3 directions x 5 request delays (1,3,4.5,5,6 s) = 60 cases per seed. Each case starts from a fresh independent stop/adjust/rise setup; an early accepted walk cannot contaminate a later timing request. After a refusal, neutralize for 150 ms and issue a new request every 250 ms until that case's gait deadline; record the original timed decision separately from first accepted gait. Report both initial/post-handoff readiness times. A held refused stick cannot fire, and acceptance at the initial 1 s request is not required for usefulness. Alternate lower commands 0.60/0.70 by seed/case parity. Development at most 120 loaded nominal cases per attempted candidate; validation 180 for the one selected candidate. Add empty-hands/lowered-arms startup/approach cases for each direction and delay (15 per seed): these must pass before the empty approach in E; loaded calibration is not assumed valid for empty hands.
- In-scope negative cases: for each of the 4 mass/carry configurations and seed, request walk/turn while (a) height remains 0.60, (b) waist pitch remains 0.20, (c) reference is still rising, (d) arm tracking error is deliberately >0.10 rad, (e) feedback has a 150 ms gap, (f) controller input has a 200 ms gap. Six cases/configuration/seed; make the request after the posture/reference violation is visible, or 100 ms into the feedback/input gap after its 50 ms budget expires. Require refusal then and during the remaining violation; report the initial, not-yet-observable part of each gap separately without claiming instantaneous loss detection. Recovery is tested after correction and fresh re-arm.
